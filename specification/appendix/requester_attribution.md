# Examples: Requester Attribution

The examples below illustrate how [Principal ID](#col) and [Credential ID](#col) are populated in the [Cost and Usage](#ds) dataset across technology environments. Each scenario shows which levels of the [requester](#term) are represented: the [principal](#term) to which access to a [resource](#term) or [service](#term) is granted, the [credential](#term) presented on the request that produced the [charge](#term), both, or neither. Provider, customer, and identifier values below are illustrative.

## Attribution Roles

The two columns answer different questions about the same [charge](#term):

* [Principal ID](#col) is the attribution dimension. A [principal](#term) persists while the [credentials](#term) that authenticate it rotate, so grouping by [Principal ID](#col) combines a user's or workload's [charges](#term) regardless of how each request was credentialed.
* [Credential ID](#col) is the audit dimension. It separates [charges](#term) that share a [principal](#term) but originate from different [credentials](#term), and joins to the [credential](#term) identifiers a [service provider](#term) records in its own logs.

Both columns identify the [requester](#term) associated with a [charge](#term). Neither identifies the party that benefits from it. The two are frequently different: a shared workload, a gateway, or an embedded assistant initiates usage for employees, clients, or end users who do not appear in the billing data at all. Where a [principal](#term) is also the beneficiary (e.g., a seat holder using their own seat, an engineer running their own query), that is a property of the scenario rather than something either column asserts, and a [practitioner](#term) cannot tell the two situations apart from these columns alone.

[Principal ID](#col) carries an identifier that references the [principal](#term), and [Credential ID](#col) carries an identifier that references the [credential](#term). Neither column contains a value that authenticates a request (e.g., a key string, a bearer token, a session cookie). Where an API key is itself the [principal](#term), as in Scenario 11, [Principal ID](#col) carries the identifier the [service provider](#term) publishes for the key, not the key string. Where a [service provider](#term) authenticates a request but publishes no identifier for the [credential](#term) presented, [Credential ID](#col) is null, as in Scenario 8.

Either identifier is null when the [charge](#term) is not associated with an entity of that kind, and also when the entity associated with the [charge](#term) has no published identifier.

The two columns are independent: a [charge](#term) may carry a [principal](#term) with no [credential](#term) identifier (Scenarios 7 through 11), a [credential](#term) with no [principal](#term) identifier (Scenario 13), both (Scenarios 1 through 6, and 12), or neither (Scenario 14). Neither column repeats the other's value, and column placement follows the *service provider's* identity and access management model rather than the kind of artifact presented: an API key is the [credential](#term) where it authenticates a [principal](#term) behind it (Scenario 1), and is itself the [principal](#term) where access is granted to the key directly (Scenario 11).

> **Note:** A [credential](#term) is what the request carries, not the factor used to log in. A password or a single sign-on assertion is exchanged at login for a session, and the request that produces a [charge](#term) carries that session, so the identifier a [service provider](#term) assigns to that session is what [Credential ID](#col) records. Where a [service provider](#term) establishes no session that it identifies separately from the [principal](#term), [Credential ID](#col) is null. Scenarios 6 and 7 show the same login path for [service providers](#term) that differ on this point. Session identifiers are commonly reissued on each login, so [Credential ID](#col) is expected to be higher-cardinality and shorter-lived than [Principal ID](#col). A session in this sense is an authenticated session. A conversation or agent session is a unit of work rather than a [credential](#term), so its identifier populates [Credential ID](#col) only where the [service provider](#term) issues a [credential](#term) for each such session and identifies it, as with the per-run federated session in Scenario 5.

## Scenarios

1. **Generative AI API, User-Owned Key:** Acme Corp runs inference on Aura Web using an API key that Alex Rivera created under their own user account. Aura Web resolves the key to that user, so the user is the [principal](#term) and the API key is the [credential](#term). Grouping by [Principal ID](#col) combines this [charge](#term) with Alex Rivera's other activity; grouping by [Credential ID](#col) isolates the spend driven by this one key.
2. **Generative AI API, Service Account Key:** Acme Corp uses an internal bot to summarize notes via a LatticeScale API. The bot authenticates with an API key issued to a service account, which LatticeScale records as the [principal](#term). The employees whose notes are summarized are not represented in either column.
3. **Multi-Tenant PaaS:** A shared BI engine runs a query on OmniQuery for a specific client of GearPeak Outdoors. OmniQuery grants access to the engine's service account, which is the [principal](#term), and records the API key the engine presented as the [credential](#term). Every client's queries resolve to the same [principal](#term), so these columns cannot separate [charges](#term) by client.
4. **Network Edge Processing:** At Acme Corp, traffic routed through an Aura Web edge network authenticates as a gateway service account presenting a gateway key. Aura Web records the service account as the [principal](#term) and the key as the [credential](#term). The end users behind the aggregated traffic are not resolvable in the billing data at any grain.
5. **Workload Identity:** A deployment pipeline at Acme Corp exchanges a short-lived federated token for a session with a LatticeScale service. The service account the token maps to is the [principal](#term), and the federated session each exchange establishes is the [credential](#term). LatticeScale assigns each federated session an identifier, which is what [Credential ID](#col) carries; the token itself is never published. A new session is established on every pipeline run, so [Credential ID](#col) changes across [charges](#term) that share a [Principal ID](#col), which is why attribution reporting reads the [principal](#term) rather than the [credential](#term).
6. **Direct PaaS Usage, Session Recorded:** A data scientist at Acme Corp logs into a LatticeScale managed notebook through single sign-on with their individual identity. LatticeScale grants access to that user identity, which is the [principal](#term), and identifies the resulting console session separately, so the session is the [credential](#term), and [Credential ID](#col) carries the identifier LatticeScale assigns to it.
7. **Direct PaaS Usage, No Session Recorded:** An engineer at Acme Corp runs a query from the StackLens console after signing in through the same organizational identity provider. StackLens attributes the [charge](#term) to the user but does not identify the session separately from the user, so [Principal ID](#col) carries the user and [Credential ID](#col) is null.
8. **Credential Without a Published Identifier:** Acme Corp calls a Meridian AI service with an API key issued to a named user. Meridian AI authenticates the request and resolves the key to that user, so [Principal ID](#col) carries the user, but it assigns no identifier to the key that it publishes in billing data. The only value that would distinguish this [credential](#term) is the key string itself, which is secret, so [Credential ID](#col) is null. Presenting a [credential](#term) alone is not sufficient for [Credential ID](#col) to be populated.
9. **Seat-Based SaaS:** Acme Corp pre-purchases SprintCanvas seats assigned to individual users. SprintCanvas grants each seat holder access under its own identity and access management model, so the seat holder is the [principal](#term). The [charge](#term) is a recurring seat license rather than the product of an individual request, so no [credential](#term) is associated with it and [Credential ID](#col) is null.
10. **Seat-Plus-Token SaaS:** Acme Corp subscribes to PipelCRM and uses its embedded AI assistant. The seat license and per-token AI usage are reported as separate [charges](#term) under the same seat holder, so attribution follows the user as [service providers](#term) shift from seat-based to hybrid seat-and-consumption pricing. The seat license is not the product of an individual request, and PipelCRM does not identify a session for the assistant's requests separately from the seat holder, so neither [charge](#term) is associated with a [credential](#term).
11. **API-Key-Only IAM Model:** Acme Corp sends transactional email through PulseMail, whose identity and access management model defines API keys as the entities to which access is granted, with no user or service account behind them. The key is therefore the [principal](#term), and [Principal ID](#col) carries the identifier PulseMail publishes for the key. A [credential](#term) is distinct from the [principal](#term) it authenticates, so these [charges](#term) are not associated with any [credential](#term) and [Credential ID](#col) is null.
12. **Marketplace Purchase:** Acme Corp purchases a Meridian AI subscription through the Aura Web marketplace and consumes it under an Aura Web console session. Meridian AI is the [service provider](#term) and Aura Web is the host provider and the [*data generator*](#metadata.datagenerator). The [principal](#term) and the [credential](#term) are both defined in the host provider's identity and access management model, because that is where the purchase was authenticated.
13. **Credential Without a Principal Identifier:** Acme Corp runs an evaluation workload on Solora AI using an API key issued to a service account. Solora AI publishes an identifier for the key but none for the service account the key authenticates, so [Principal ID](#col) is null, and [Credential ID](#col) carries the key's identifier.
14. **Billing System Charge:** Acme Corp receives a promotional credit or is charged applicable tax from LatticeScale. The [charge](#term) originates in the *service provider's* billing system and is not associated with a [principal](#term) or a [credential](#term), so both columns are null.

Every [Credential ID](#col) value above is an identifier a [service provider](#term) assigns to a [credential](#term) and publishes, not the [credential](#term) itself. Scenarios 7 through 11 show the reasons the column is null, and each maps to one of the two null conditions: in Scenario 8 the [credential](#term) presented has no published identifier, while in the others no [credential](#term) is associated with the [charge](#term), whether because no session is identified separately from the [principal](#term) (Scenario 7 and the per-token usage in Scenario 10), the [charge](#term) is not the product of an individual request (Scenario 9 and the seat license in Scenario 10), or the presented key is itself the [principal](#term) (Scenario 11).

The Principal Type and Credential Type columns are not FOCUS columns. They show the value a data generator would carry in the `Type` property of the `Principal` and `Credential` entries in [Requester Details](#col), and are included here to contrast the values that could be used in different scenarios.
