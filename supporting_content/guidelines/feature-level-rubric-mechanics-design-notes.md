# Feature-Level Rubric: Mechanics Design Notes

This document records the thought process behind the [feature-level rubric mechanics guideline](../../guidelines/contributors/feature-level-rubric-mechanics-guidelines.md) (FR 2335; the principles guideline entered review in PR 2507, and the mechanics guideline follows it): the choices its machinery makes, the alternatives considered, and the questions still open. It is development background, not specification content, and parts of it describe analysis that is ongoing. Where a column level appears here, it is the output of reasoned analysis under the draft rubric, not a proposal to change any column. It accompanies the [principles design notes](feature-level-rubric-design-notes.md), which record why the rubric levels by operating model and why Mandatory is earned, and the [blind-rater evidence](feature-level-rubric-blind-rater-evidence.md), which records how the principles text was tested; several mechanics choices below respond to what that testing surfaced.

## The Job the Mechanics Do

The principles set the bar: two people applying the rubric to the same column reach the same level, without the author in the room. The mechanics exist because the level alone is not enough to hold that bar. Two readers can agree a column is Conditional and still disagree on which operating model Condition gates it, which primary a refining column points at, or which kind of gate is being recorded, and each of those expressions is a lever an author could pull to reach a preferred outcome by another route. So the mechanics aim at reproducibility of the level and its expression together, and every artifact they introduce (the matrix, the refines-pointer, the records) is shaped so the author is never the sole voice on their own column's inputs. Author-independence is deliberately stated once, as a single review rule in the guideline's overview, rather than restated per mechanism: one rule is auditable, while scattered restatements drift apart.

## Counting Operating Models

The threshold counts operating models, so whoever controls how models are sliced controls the count. The specification's Conditions section defines twenty-five operating model Conditions today; taken as free combinations they describe tens of millions of distinct profiles, and an author could split or merge near-duplicate profiles until the count said what they needed. The guideline closes this by normalizing the count to the column: for a given column, profiles that differ only on Conditions that do not gate that column collapse into one operating model. A Condition the column does not depend on cannot move the column's count, which removes the incentive to assert or invent unrelated Conditions, and the resulting enumeration is small enough for a reviewer to confirm against the Conditions section.

## One Independent File for the Gating

The applicability matrix could have been a generated view over the dataset requirements, which would be cheap and never out of date. The guideline instead makes it a standalone, separately reviewed file, because the two designs answer different questions. A generated view re-renders whatever the requirements already say, so it can never catch an error in them; an independently authored expected-state can disagree with the requirements, and a reconciliation check turns each disagreement into a finding. The cost is real (a second artifact to maintain), and it is only worth paying if the reconciliation check exists, which is why the guideline treats that check as non-optional and reads every surface a gate can appear on rather than the column table alone. The initial population of the file is timed to follow the requirements-model changes, so the file and the model start reconciled instead of diverging on day one.

The two data files beside the matrix follow the same instinct. The derivation source records direction explicitly, because a symmetric record would let a cost be read as derivable from a unit price, which the principles rule out. The Conditions map is allowed to be partial, with an explicit unmapped-key finding, because the alternative designs both hide information: failing the build on the first unmapped key blocks unrelated work, and silently dropping unmapped keys makes the map look complete when it is not.

## A Check That Flags, Not Decides

The machine-readable check's first release only flags a column whose authored level diverges from what its recorded gates and derivation imply; a human resolves the flag. Two facts drove this shape. First, the check must read the level a column's file actually authors, because nothing else in the model carries it: in the 1.4 requirements model, rules whose identifier ends in the Conditional status suffix span every keyword strength (hundreds at `MUST`, dozens at `SHOULD` and `MAY`), so the suffix cannot stand in for a feature level. Second, an automated Mandatory-versus-Conditional verdict needs the calibrated threshold and complete Supported-Feature coverage, and neither input exists yet. A check that pronounced verdicts from today's inputs would be precise about data that is not there.

## Recording Assertions from the Schema

The principles establish that asserting an operating model Condition is not a separate registration step, and leave to the mechanics where an assertion is recorded. Two designs were considered. The guideline's answer is that the published dataset is the record: its metadata names the columns present, a presence-gated column is present exactly when its gating Condition holds, so the asserted set can be read from the schema with no side channel, and including a gated column binds the generator to the Condition's obligations rather than being disclaimable. The alternative, an explicit metadata field listing asserted Conditions, would make the record self-describing rather than inferred, and it may yet be worth adding; it is deferred rather than rejected because it is a specification change with unsettled questions (its scope, how it evolves, and which record governs when the declaration and the observed schema disagree). Reading from the schema needs no specification change and is enforceable now.

## A Method Now, a Number Later

The applicability threshold is deliberately split into a method that is normative now and a number that is not set yet. The method (count operating models normalized to the column, read the matrix, treat one unusual model as a recordable exception and a pattern of two or more as Conditional) does not change when calibration arrives; only the pattern test is replaced by a prevalence share over a conformance census. The number is not set now because there is no census in the repository to set it from, and picking a cutoff by debate would launder a guess into a calibration. The interim rule exists so columns are actually leveled in the meantime. One sentence was added after testing: when independent readers applied the principles text to boundary columns, several acknowledged the boundary and still chose Mandatory, treating the Conditional default as advisory, so the guideline now states the default is binding and the only path to Mandatory at the boundary is the recorded exception.

## A Pointer, Not a Judgment, at the Necessity Boundary

The necessity carve-out (a column that only refines a result a Mandatory primary already delivers is Recommended) turns on which column is "the primary", and that is the kind of call two readers make differently. The guideline makes it an artifact: a refining column carries a one-line pointer naming the Supported Feature and the primary, the primary comes from a per-feature mapping rather than the author's choice, and a reviewer confirms the pointer. The mapping waits on Directly Dependent Columns coverage, so in the interim the pointer is authored and independently confirmed. A rerun of a feature's example query was considered as the test itself and rejected: it trusts an author-written query, and many features have no runnable query, so behavior can only falsify a pointer (structure says refines, the rerun says breaks), never demote a column on its own.

## The Category-Defaults Firewall

The informative layer records, per category, the operating model Conditions typically met in that category today. The design constraint is that nothing that determines a level may be able to read a category, or category defaults quietly become category rules, which is the failure the rubric exists to end. The requirements-model build assembles the model from the model rules directory alone and parses nothing under the Conditions section, so the firewall holds today; annotating the Conditions section, or any file a level-determining check consumes, with category strings would put categories one read away from the leveling path. That is why the table lives in the guideline, physically outside every file the check consumes, with its referential integrity held by a markdown-lint rule rather than the requirements-model test layer.

## Records the Build Enforces

The records registry and the per-rule leveling-justification field record the same decision twice, on purpose. The registry is the human-auditable home, a versioned file that participates in include validation so an entry cannot rot silently; the model field is machine-enforced, failing the build when a Mandatory-by-exception rule lacks its justification. A registry alone can drift from the rules it describes; a model field alone is invisible to a reader following a leveling debate. The derivation fields (`DerivesFrom`, `RelationKind`) ride the same requirements-model change set, so the derivation source is assembled from the model rather than from prose equalities scattered across column files.

## Design Questions Still Open

* **The necessity boundary has no interim default.** The applicability boundary defaults to Conditional; the refines-versus-breaks boundary has no equivalent rule. In the most recent testing of the principles text (recorded in the [blind-rater evidence](feature-level-rubric-blind-rater-evidence.md)), none of six independent readers placed BillingAccountName at Mandatory, and different readers reached the demotion by different routes, which suggests the gap is in the text rather than the readers. Whether the carve-out should demote a display-name column that sits under a Mandatory identifier, and what the interim default at this boundary should be, is a working-group question this guideline deliberately does not pre-answer.
* **One model or a pattern.** The interim rule treats a single unusual operating model as a recordable exception that can keep a column Mandatory, and a pattern of two or more as Conditional. The counter-position is that one genuine operating model that lacks a concept should flip the column by itself. The calibrated threshold will eventually answer this from data; until then the recorded-exception path is the pressure valve, and the question stays open.
* **An explicit assertion declaration.** Reading assertions from the schema is the record for now; whether a metadata field listing asserted operating model Conditions is worth its specification change remains open.
* **The level set itself.** Two procedure steps output Recommended (useful-but-not-needed, and derivable outside a symmetry group). A change to the specification's level set would change those outputs, so the procedure is written against the current four levels and will need revisiting if the set changes.
* **The Condition vocabulary's name.** Renaming the concept to Operating Model Conditions is being pursued separately with the maintainers; the guideline and these notes read correctly under either name.

## Relationship to the Principles and Their Notes

The principles guideline carries what is stable; the mechanics guideline carries the machinery; the split lets the principles be adopted while the machinery's data prerequisites are still being built. The [principles design notes](feature-level-rubric-design-notes.md) record why the operating model is the leveling basis, why Mandatory is earned, and the applicability-matrix method with its dry run; this document does not restate that material. What this document adds is the record of the mechanics' own choices: where each artifact came from, what it replaced, and what is still unsettled. Links to the principles guideline and its companion documents resolve once the principles land; the mechanics follow them by design.
