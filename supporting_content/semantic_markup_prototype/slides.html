FOCUS Working Group · Proposal

Mark what it means, not how it looks

Moving FOCUS source files from formatting-based markup to semantic tags, with the formatting applied by the build. A working prototype is included.

David Moreau
Coinbase

Updated 30 October 2026 with a conversion and semantic review of the whole specification

This is a proposal to change how we write the FOCUS source files. Today every author hand-writes the links and formatting the published spec needs. The proposal is that authors only say what a reference is, such as a column, a glossary term or an allowed value, and the build turns that into links and formatting. I built a small working prototype to test it, and the results are later in the deck.

This is the core problem. When an author writes resource type, we can’t tell whether they mean the column. Italics mean both glossary term and emphasis. A ColumnId in plain text could be misspelled and nothing would notice. We can’t lint our way out of this, because the information isn’t in the source. Each new kind of entity also needs another visual convention, and we are running out.

FOCUS semantic markup · 6

Here is the proposal in one picture. Authors tag what a reference is. A registry is generated from the files that already define each entity: column files, the glossary, attributes and operating model conditions. Nobody maintains it by hand. A resolver step in the build looks up every tag and applies the formatting rules, so everything after it sees ordinary Markdown. The same source can produce the full spec, a per-file preview that links to source files, and a lint report.

The tag is a normal Markdown link

Our glossary links already work this way: #glossary:charge names a term, not a location. Any other link passes through unchanged.

FOCUS semantic markup · 7

The syntax is deliberately boring. The link target names an entity type, and optionally an ID, instead of a location. When the link text already matches the ID, you leave the ID off. A column that exists in several datasets can name its dataset, and a file outside the datasets folder can set a default dataset in front matter so it rarely has to. The same pattern covers JSON objects, schemas and metadata fields. This isn’t new to us: our glossary links already work this way. Ordinary links, such as appendix links, keep working unchanged, so old and new markup can coexist during migration.

Later mentions don’t

Changing a rule, such as how columns are styled, becomes one edit to the build instead of a thousand edits to the source.

Today’s conventions from the Editorial Guidelines, applied by the resolver · 9

These rules are the ones we follow today. The difference is that the resolver applies them, so they are applied the same way everywhere. The last one is new: when a tag names an ID explicitly, that ID decides the entity, and if the visible text names a different entity the build reports it. That is how the conversion found a link whose text and target disagree. If the working group decides to change a convention, for example to style columns differently or to link every mention in the Requirements section, that becomes one change in the build. Today it would mean editing every file.

Definition checks run against working_draft · 10

A common question is whether we also tag the definitions. We don’t need to. Column files, the glossary, the Allowed Values tables, and the ID and name sections of every other entity are already very regular, so the registry reads definitions from that structure, and the build checks the structure every time. 149 of 150 column files pass today. The one exception is a new SKU Price column whose Allowed Values table has an unexpected header, which is exactly the kind of thing the check is for. The checks also found eight names that belong to two kinds of entity. For example, billing currency is both the BillingCurrency column and a glossary term. That’s why a reference has to say what kind of entity it is. Aliases go in optional front matter on the defining file.

FOCUS semantic markup · 16

I looked at the obvious alternatives. Custom tags like column read well on GitHub, but Pandoc sees them as separate pieces of raw HTML, and our linter flags inline HTML. Pandoc spans are clean in Pandoc but show the braces literally on GitHub. Remark is a good tool, but it would add Node.js and a second Markdown parser next to Pandoc, and the Pandoc tree is the one that produces the spec. The link form works everywhere today with no new tooling.

For those who know the build: it barely changes. A script generates the registry and checks the definitions. The vendored markdown-pp include module marks where each file starts and drops front matter. Then a resolver step turns the tags into the same Markdown links we write by hand today, right after markdown-pp, so the linter, Pandoc and the PDF step all see ordinary Markdown. FOCUS semantic markup · 18

The migration is incremental. First the tooling runs in warn-only mode, so nothing changes for authors. Then a script converts the files. It is safe to rerun, and a comparison sorts every rendered difference by kind. Then a person reviews the result for meaning and decides what the script listed, such as a name that is also a glossary term. Keeping that review as its own commit means the script can be rerun whenever the spec changes, and the review can be compared, reviewed or rolled back separately. The demo branch has done the first three steps for the whole spec. Converting touches hundreds of files at once, so we still need to choose between one conversion on a quiet day and an area at a time. Once the spec is clean, strict mode stops new drift from merging.

These are the decisions that are ours to make before scaling up. The first three came out of converting the whole spec, and the next three slides take them one at a time. Tables outside Content Constraints are the biggest: catalog tables link every row and example tables don’t, and no rule says which is which yet. Names that are also glossary terms, like SKU Price, needed a person in 208 places, and #2765 already proposes a rule that would let the script decide most of them. Dataset scope has a recommendation, a default per file, but files that mix datasets still need a qualifier on each mention. Plain prose is still open. And merging a change of this size needs a plan, because every open pull request would conflict.

Which tables should link every row?

Catalog tables

Each row names a different entity, like the Columns table in dataset.md. Readers land on a row and expect its link.

Example data tables

Rows repeat the same columns and values. Linking every row would repeat the same link down the table.

Today only Content Constraints rows always link. The conversion left 231 hand-written links in 37 files as written until there is a rule.

Proposed: a reference links at its first mention within each table, and tables don’t affect first mentions in the prose around them.

Question 1 of 3 · the entity catalog table rule proposed in #2514 and #2765 · 20

The Editorial Guidelines say Content Constraints tables link every reference. Other tables are where the conversion stopped. A catalog table, such as the list of columns at the top of each dataset, names a different entity on every row, so every row should link. An example data table repeats the same columns and values, so linking every row just repeats the same link. The proposal handles both with one rule: a reference links at its first mention within each table, so a catalog links every row and an example table links once, and tables don’t change which mention in the surrounding prose counts as the first. Until we agree, those 231 links stay hand-written.

Question 2 of 3 · names shared by a dataset or column and a glossary term · 21

Some names belong to two kinds of entity. SKU Price is a dataset and a glossary term; List Unit Price is a column and a glossary term; Billing Period is a dataset and a glossary term. The script can’t tell which is meant, so it left 208 of them for a person. In the review, the cues were consistent: a name followed by record or dataset meant the dataset, a column’s Display Name capitalization meant the column, and the rest was the concept in ordinary prose. #2765 already proposes the capitalization rule. If we adopt it, together with the record and dataset cues, the script can decide most of these itself, and people only see the leftovers.

Question 3 of 3 · the dataset scope question in #2779 · 22

A column like BilledCost exists in both Cost and Usage and Invoice Detail, so a reference has to say which one it means. Column files already know, from their folder. Other files can say it once in front matter, and the script inferred that default for 57 files from the columns they already reference. The hard case is a page that really is about two datasets, like the rate optimization supported feature, which compares SKU Price records with Cost and Usage charges. There every shared column needs a qualifier, 190 times across 11 files. That is explicit, but verbose. A default per section would let those pages say it once per section instead.

Four rule changes: two now checks, two to settle

One rule for tables

Outside Content Constraints, link at the first mention within each table; tables don’t affect the prose.

Self-links by anchor

No link to the section a reference sits in, or its parents, instead of no link to the file’s own entity.

Tags in headings · done

Now an error, FOCUS017. No heading has one, so the question of how to render them doesn’t arise.

From the rules review in CONVERSION.md: 11 findings, these four high priority · 23

After the full conversion I reviewed the tagging rules themselves against how they behaved at scale. Most held up. These four were where the rules were inconsistent or silent. Two are now settled as checks: a tag in a heading, and italics inside a tag, are both errors. Neither occurs anywhere in the converted spec, so making them errors costs nothing and keeps it that way. The other two still need us. Tables follow three different behaviors today, and one rule would cover them. And the no-self-link rule is based on files, so it needed exceptions for JSON objects and for Data Generator; deciding by anchor removes them.
